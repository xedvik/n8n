# Мастер настройки `/setup/`

Мастер — часть единого Docker Compose-стека. Публичный адрес:

```text
https://<domain>/setup/
```

## Первый вход

Откройте first-run ссылку из вывода установщика:

```text
https://<domain>/setup/?token=<одноразовый-токен>
```

Мастер сам считывает подтверждение из ссылки и очищает URL. Введите имя администратора, пароль и подтверждение. Ручной ввод токена не требуется.

Если ссылки нет, мастер не открывает регистрацию и показывает безопасную инструкцию. Повторное использование ссылки невозможно: после создания администратора она удаляется, а вход выполняется по логину и паролю. Восстановление пароля через мастер **НЕ РЕАЛИЗОВАНО**; администратор сервера должен создать новую установочную ссылку.

## Пять этапов

1. **Начало работы** — проверка n8n, подключение по API key, адрес приёма заявок и OAuth callback.
2. **Настройка компании** — название компании и часовой пояс.
3. **Подключение интеграций** — HubSpot, Google Sheets, Telegram; необязательные сервисы можно пропустить.
4. **Проверка и запуск** — проверка системы, тестовая заявка, безопасное применение настроек.
5. **Готово** — панель состояния системы и переход к работе.

Технические параметры вынесены в **«Дополнительные настройки»**: маппинг полей, идемпотентность, retention и повторная обработка. В **«Обслуживании»**: сервисы, операции, восстановление, резервные копии и проверка системы.

## Статусы

Статус этапа вычисляется по фактическим результатам:

- Не начато.
- Требует действий.
- Настроено, но не проверено.
- Проверено.
- Ошибка.

Наличие сохранённого доступа само по себе не даёт статус «Проверено». Для CRM, таблицы, Telegram и тестовой заявки нужен подтверждённый результат проверки.

У каждой интеграции независимый scope: он учитывает только её режим, credential, выбранный чат, таблицу и вкладки. Проверка HubSpot не сбрасывается изменением Telegram, и наоборот. Общие изменения (компания, timezone, маппинг) сбрасывают только сквозную проверку и doctor, но не подтверждения доступности отдельных сервисов.

## Подключение n8n

1. Откройте n8n по ссылке из Мастера.
2. Создайте владельца, если открываете n8n впервые.
3. Откройте Settings → API.
4. Создайте API key с правами:
   - `workflow:read`
   - `workflow:update`
   - `workflow:activate`
   - `credential:list`
   - `credential:read`
   - `credential:create`
5. Скопируйте ключ и вставьте в Мастер.
6. Нажмите «Подключить n8n».

Ключ проверяется server-side, шифруется AES-256-GCM и не возвращается в браузер, API, DOM, storage или логи.

## Telegram

После ввода токена нажмите «Проверить подключение». Мастер вызывает Telegram Bot API `getMe` и `getUpdates`, показывает доступные чаты и позволяет выбрать чат из списка. Если список пуст, отправьте боту сообщение и повторите; ручной Chat ID остаётся резервным вариантом.

## Google Sheets

Для сервисного аккаунта доступно создание таблицы, вкладок и заголовков. Если таблица уже указана, мастер добавляет отсутствующие вкладки и обновляет первую строку заголовков, не изменяя строки данных. OAuth2 требует ручного входа в n8n.

## Безопасное применение

Кнопка «Сохранить и применить» используется и для основного запуска, и для «Дополнительных настроек». Отдельного сохранения `client.json` в обход применения нет.

1. проверяет и нормализует конфигурацию;
2. готовит доступы к сервисам;
3. сохраняет backup текущего workflow в `wizard-data/workflow-backups/`;
4. сохраняет точку восстановления `client.json`;
5. сохраняет конфигурацию;
6. обновляет workflow;
7. запускает doctor.

Перед сохранением мастер фиксирует предыдущий hash конфигурации. Если doctor возвращает `FAIL` или `UNVERIFIED`, это считается неуспешным применением: мастер восстанавливает backup конфигурации, проверяет совпадение hash, затем восстанавливает workflow из серверного snapshot и проверяет фактическое состояние. Если что-то не удалось восстановить, интерфейс показывает **«Применение частично выполнено»** с инструкцией проверить конфигурацию и workflow. Атомарность внешних API не обещается.

Изменение timezone или других настроек помечает конфигурацию как несохранённую, сбрасывает doctor/тестовую заявку и старые результаты интеграционных проверок. Уйти со страницы с несохранёнными изменениями можно только после подтверждения; закрытие страницы также предупреждает.

## Результаты проверок

Успешная проверка интеграции сохраняется на сервере в `wizard-data/integration-verifications.json` только как безопасные метаданные:

- тип интеграции;
- результат и статус;
- время проверки;
- scope, рассчитанный по релевантным параметрам интеграции (credential, режим, таблица, чат), а не только по общему hash конфигурации.

Изменение одного credential инвалидирует только его проверку. Общий hash конфигурации остаётся идентификатором применённой конфигурации и используется для сквозного теста.

Токены, service account JSON, chat ID и другие данные интеграций в этот файл не попадают. Запись защищена правами `0600`.

После перезагрузки результат показывается как **«Последняя проверка прошла»**, но не как текущая доступность: для зелёного статуса нужно повторить проверку. Выбирается последняя запись для того же scope; PASS от другой конфигурации не подставляется. Исторический PASS не считается доказательством доступности внешних API.

Сквозной тест (`Отправить тестовую заявку`) подтверждает задействованные сервисы целиком и снимает необходимость повторять эквивалентные одиночные проверки. Итоговая готовность считается только при актуальном doctor PASS и актуальном сквозном тесте PASS; иначе интерфейс перечисляет конкретные недостающие проверки.

## Doctor и предупреждения

Строки doctor окрашиваются по уровню: `OK` — зелёный, `WARN` — жёлтый, `FAIL` — красный, `INFO` — нейтральный. Общий PASS не делает отдельные WARN зелёными.

Предупреждение о `needs_reconciliation` показывается отдельным жёлтым блоком со ссылкой на «Обслуживание», где видны ID операций. Оно не блокирует готовность, если относится к старой независимой операции, но не скрывается.

## API

Основные endpoints (снаружи с префиксом `/setup/`):

```text
GET  /api/auth/status
POST /api/auth/register
POST /api/auth/login
POST /api/auth/logout
GET  /api/bootstrap
POST /api/n8n/connect
POST /api/config/validate
POST /api/config
GET  /api/config/backups
POST /api/config/backups
POST /api/config/restore
POST /api/verifications
POST /api/workflow/backups
POST /api/workflow/restore
GET  /api/services
GET  /api/operations/summary
GET  /api/operations
POST /api/operations/:id/retry
POST /api/google/provision
POST /api/credentials
POST /api/integrations/test
POST /api/workflow/apply
POST /api/workflow/install
POST /api/doctor
```

POST-запросы требуют `X-Wizard-Token`; все API, кроме health/auth, требуют административную сессию.

## Ограничения

- Живой OAuth Connect выполняется в n8n вручную.
- Google Service Account требует шаринга таблицы на `client_email`.
- `doctor --integration-test` использует фиксированный тестовый email и может обновить существующий контакт HubSpot.
- Реальная тестовая заявка отправляется только после подтверждения.
- Kit не гарантирует exactly-once для внешних API; неоднозначные стадии требуют проверки.
